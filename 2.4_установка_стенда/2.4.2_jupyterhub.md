# Развернуть материалы в JupyterHub

Документ для того, кто настраивает JupyterHub, и для участника, который в нём
работает. Локальная установка описана отдельно — [УСТАНОВКА.md](2.4.1_установка.md).

Тетради практики устроены просто: обычные ядра Python, никаких расширений хаба
не требуется. Чтобы они заработали в корпоративном контуре, должны сойтись три
вещи: **библиотеки в образе ядра, сетевые доступы и переменные окружения.**
Ниже — каждая по отдельности и проверка, которая покажет, что всё сошлось.

## 1. Библиотеки в образе ядра

Python 3.10 или новее и пять библиотек:

```
jupyter>=1.0   psycopg2-binary>=2.9   pandas>=2.0   matplotlib>=3.7
requests>=2.31   tabulate>=0.9
```

Если образ ядра собирается централизованно — добавьте их в образ:

```dockerfile
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt
```

Если участники ставят сами и в домашней папке разрешена запись:

```bash
pip install --user -r requirements.txt
```

## 2. Сетевые доступы

| Куда | Зачем | Адрес |
|---|---|---|
| База данных | все тетради с SQL | ваш сервер СУБД, порт 5432 |
| Авторизация GigaChat | получение токена | `ngw.devices.sberbank.ru:9443` |
| API GigaChat | запросы к модели | `gigachat.devices.sberbank.ru:443` |
| BI-система | кейс с дашбордами | внутренний адрес вашего BI |

Если наружу ходят через прокси, ядру нужны `HTTPS_PROXY` и `NO_PROXY`
(во втором — адреса базы и BI, чтобы внутренний трафик не уходил в прокси).

### Сертификаты

Сертификат GigaChat подписан НУЦ Минцифры. Если этой цепочки нет в образе,
обращение падает на проверке TLS. Правильный путь — положить сертификаты
в образ:

```dockerfile
COPY russian_trusted_root_ca.cer /usr/local/share/ca-certificates/russian_trusted_root_ca.crt
COPY russian_trusted_sub_ca.cer  /usr/local/share/ca-certificates/russian_trusted_sub_ca.crt
RUN update-ca-certificates
ENV GIGACHAT_VERIFY=1
```

Клиент ассистента (`tools/llm.py`) читает две переменные:

- `GIGACHAT_VERIFY=1` — проверять цепочку системным хранилищем;
- `GIGACHAT_CA_BUNDLE=/путь/к/bundle.pem` — проверять указанным файлом.

Без них проверка выключена: на учебной машине цепочки обычно нет, и практика
иначе останавливается на установке сертификатов. **В корпоративном контуре
одну из этих переменных нужно задать** — иначе трафик к модели идёт без
проверки подлинности сервера.

## 3. Переменные окружения

| Переменная | Кто задаёт | Пример |
|---|---|---|
| `GIGACHAT_AUTH_KEY` | администратор, из секретницы | строка Base64 |
| `GIGACHAT_SCOPE` | администратор | `GIGACHAT_API_CORP` |
| `GIGACHAT_MODEL` | администратор | `GigaChat-2-Max` |
| `GIGACHAT_VERIFY` или `GIGACHAT_CA_BUNDLE` | администратор | `1` |
| `PGHOST`, `PGPORT`, `PGDATABASE` | администратор | адрес вашей базы |
| `PGUSER`, `PGPASSWORD` | администратор, из секретницы | сервисная учётка на чтение |
| `MB_URL` | администратор | адрес BI, если он используется |

Тетради не знают ничего, кроме этих имён: сменить учебную базу на рабочую —
значит поменять значения `PG*`, править код не нужно.

### Способ 1. Всем участникам одинаково

`jupyterhub_config.py`:

```python
import os

c.Spawner.environment = {
    "GIGACHAT_SCOPE": "GIGACHAT_API_CORP",
    "GIGACHAT_MODEL": "GigaChat-2-Max",
    "GIGACHAT_VERIFY": "1",
    "PGHOST": "analytics-db.internal",
    "PGPORT": "5432",
    "PGDATABASE": "analytics",
    "PGUSER": "workshop_ro",
    # значения секретов берём из окружения процесса хаба, а не из файла
    "GIGACHAT_AUTH_KEY": os.environ["GIGACHAT_AUTH_KEY"],
    "PGPASSWORD": os.environ["WORKSHOP_DB_PASSWORD"],
}
```

Сам хаб получает эти два значения из вашей секретницы — systemd `EnvironmentFile`,
Vault, Secret в Kubernetes. В `jupyterhub_config.py` секретов быть не должно:
файл почти всегда лежит в системе контроля версий.

### Способ 2. Kubernetes (zero-to-jupyterhub)

`values.yaml`:

```yaml
singleuser:
  extraEnv:
    GIGACHAT_SCOPE: "GIGACHAT_API_CORP"
    GIGACHAT_VERIFY: "1"
    PGHOST: "analytics-db.internal"
    PGUSER: "workshop_ro"
    GIGACHAT_AUTH_KEY:
      valueFrom:
        secretKeyRef: {name: workshop-secrets, key: gigachat-auth-key}
    PGPASSWORD:
      valueFrom:
        secretKeyRef: {name: workshop-secrets, key: db-password}
```

### Способ 3. Свой ключ у каждого участника

Когда ключи персональные (у каждого свой лимит и свой учёт расхода), значения
подставляются на старте сервера:

```python
def pre_spawn_hook(spawner):
    логин = spawner.user.name
    spawner.environment["GIGACHAT_AUTH_KEY"] = достать_из_секретницы(логин)

c.Spawner.pre_spawn_hook = pre_spawn_hook
```

`достать_из_секретницы` — обращение к вашему хранилищу. Читать ключи из
домашних папок участников не нужно: они попадают в резервные копии и
в выгрузки.

### Способ 4. Участник задаёт сам

Если администрирование хаба недоступно, участник кладёт файл `.env` рядом
с папкой практики — тетради читают его сами:

```
GIGACHAT_AUTH_KEY=…
PGHOST=analytics-db.internal
PGUSER=workshop_ro
PGPASSWORD=…
```

Файл перечислен в `.gitignore` и в репозиторий не попадает. Права на него
стоит закрыть: `chmod 600 .env`.

## 4. Подключение к реальной базе

Тетради подключаются через `tools/sqlcell.py`, а он берёт всё из тех же `PG*`.
То есть на рабочих данных ничего в коде не меняется — меняются значения
переменных и имена таблиц в запросах.

**Как правильно.** Отдельная учётная запись только на чтение, доступ выдан
на конкретную схему или на набор представлений, пароль приходит из секретницы
переменной окружения. Тогда тетрадь, случайно отправленная коллеге, не несёт
в себе доступа.

**Как часто делают и почему это плохо.** Логин и пароль константами в первой
ячейке:

```python
# так не надо: пароль уезжает в git, в скриншот и в экспорт тетради
conn = psycopg2.connect(host="…", user="analyst", password="Qwerty123")
```

Пароль в ячейке остаётся в файле тетради вместе с выводом, попадает в систему
контроля версий, в общий диск и в скриншот на созвоне. Замена занимает
одну строку:

```python
import os
conn = psycopg2.connect(
    host=os.environ["PGHOST"], dbname=os.environ["PGDATABASE"],
    user=os.environ["PGUSER"], password=os.environ["PGPASSWORD"])
```

Если переменных нет, а подключиться нужно сейчас, — спрашивайте пароль
в диалоге, он не сохранится в файле:

```python
import getpass
пароль = getpass.getpass("Пароль к базе: ")
```

**Другая СУБД.** Материалы написаны на PostgreSQL. При переносе на другую
СУБД меняется драйвер в `tools/sqlcell.py` и несколько конструкций: `FILTER
(WHERE …)`, `DISTINCT ON`, `percentile_cont(…) WITHIN GROUP` есть не везде.
Эквиваленты — в памятке `2.3_памятка_sql_и_pandas/2.3.1_памятка_sql_и_pandas.ipynb`: там
у каждой операции есть вариант на pandas, и он работает поверх любой базы.

## 5. Что уходит в модель, а что нет

Ассистент видит ровно то, что ему отправили: текст промпта, схему таблиц из
описания в `tools/report_agent.py` и результаты выполненных им запросов
(не более 200 строк). Числа он не выдумывает — но всё, что он получил,
покидает контур, если модель внешняя.

Отсюда правило практики, которое стоит сохранить и после неё: **в промпты
идут учебные и обезличенные данные; агрегаты и схема — можно, персональные
данные клиентов — нет.** Если модель разворачивается внутри контура, правило
мягче, но проверка «что именно уходит» всё равно делается один раз осознанно,
а не по умолчанию.

## 6. Проверка

Одна команда, которая говорит, что сошлось, а что нет:

```bash
python3 tools/check_env.py
```

Скрипт печатает библиотеки, переменные окружения, подключение к базе с числом
строк по таблицам, получение токена ассистента и доступность BI. Значения
ключей и паролей он не печатает — только «задана, длина N», поэтому вывод
можно приложить к заявке в поддержку.

| Что показал | Обычная причина |
|---|---|
| переменная не задана, хотя в хабе прописана | значения заданы процессу хаба, но не проброшены в сервер участника: `c.Spawner.environment` или `c.Spawner.env_keep` |
| `токен не получен` | закрыт доступ к `ngw.devices.sberbank.ru:9443`, нет сертификатов или ключ выдан на другую область (`GIGACHAT_SCOPE`) |
| база не подключается | нет сетевого доступа до СУБД или учётке не выданы права на схему |
| `ModuleNotFoundError` | тетрадь запущена на ядре, где библиотеки не ставились |

## 7. Чего в JupyterHub не будет

Локальный стенд поднимает ещё и BI-систему (Metabase) — в контуре банка её
заменяет ваш собственный BI. Переносится в него главное: **SQL из тетради
конвейера вставляется новой панелью как есть.** Не переносится автоматически
только тетрадь, где дашборд собирает агент: она обращается к API Metabase,
и для другого BI нужен другой набор вызовов. Логика при этом та же самая —
создать карточку с запросом, выбрать тип отображения, положить на дашборд.

      «всё на месте».
